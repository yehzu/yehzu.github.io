淺談程式的可讀性

什麼是可讀性高的程式？常常被人掛在嘴邊說這是一個見人見智的問題，但，真的是這樣嗎？基本上所有的工程師在撰寫程式的當下，都覺得自己的程式可讀性是很高的，但這往往陷入了自我感覺良好的陷阱裡面…

寫了這幾年的程式，並且一直努力在嘗試增進程式可讀性的我，對這個題目有一點想法。

首先，為什麼會說一般工程師在寫程式的當下，高可讀性是自我感覺良好呢？我想大家一定都有這樣的經驗：在新增一段需求的時候，覺得前人寫的 code 實在是慘不忍睹，因為一來看了半天才看懂這段實作，二來，看懂了實作，卻看不出為什麼要寫這段 code。正生氣時， git blame 一下卻發現是自己半年前寫的，這下可尷尬了…剛剛吐出來的髒話完全罵到了自己。

「什麼！！怎麼可能！！？」

這是很容易發生的事，因為在撰寫的當時，只有撰寫的人是最了解整段修改是為了什麼，以及每個小調整的用意。在那個當下，每一段程式碼都是你精鎚百鍊的結果（如果不是的話…那看不懂就非常應該了XD）。因此，就算程式碼真實的可讀性不好，在你的腦中也會幫中間的斷點補上連結，設計不良的介面有聲音說服自己這個很自然，總之，自己一定會覺得可讀性很好。但隨著時間過去，記憶開始淡化之後，原本在腦中連成一片的邏輯就被打回原形，程式就變得不好讀了。

怎樣才是高可讀性？#

要達到 100% 可讀的程式碼，我覺得是相當困難、甚至是不可能的。這要有非常好的程式品味，抽象分層能力，以及語言掌握功力。但縱使如此，也未必能讓人人都看得懂（先埋個伏筆XD）。如果不是這樣大神級的工程師，只是一個剛入行、或是工作幾年的工程師，就沒有辦法寫出好讀的程式了嗎？

不。可讀性不是非黑即白，而是有相對的好讀和不好讀，能夠往好讀一些的方向走，在未來需要修改或重構時，就很有價值了！網路上講可讀性的文章很多，有些常見的技巧如：為常數命名、命名方式、early return、一次做一件事，等等，這篇文章就不贅述。這篇文章想說的，是寫程式時的心態、以及程式碼會怎麼從好讀走向不好讀。高可讀性的程式碼，我認為在撰寫程式時，從以下三個方向要求自己，基本上就不會有大問題：

  1. 時時刻刻換位思考 – 把自己當成完全沒看過這段 code 的人
  2. 想像在寫書的目錄 – 注意同個 code block 中的抽象層次是否相同
  3. 不寫註解、寫註解 – 不寫廢話，寫人家不知道的東西

時時換位思考#

換位思考的重點，是把自己當作完全不懂脈絡的人，最好是把自己假想成團隊中程式能力最弱且不知道脈絡的情況。每寫完一個 method / function，先拋開已知的任何前提，單純地去看我是否能夠用這個 method 裡的所有資訊，就能得知這個 method 在做什麼？如果不行，那是缺了什麼我不知道？有沒有辦法修改程式避免這個問題？

想像在寫書的目錄#

我在讀書時會先掃過書的目錄，他是整本書的大綱及架構，有了這個概念再去讀書，就比較能了解作者寫作的安排。程式碼也是一樣的。一段程式碼片段，就像在寫書的目錄一樣，讓人快速掃過之後，就可以有大概的了解。而要知道細節，就要再往下一層去探索。

這邊用一個簡單的例子來表達這個概念，大家可以先看這段程式碼，並試圖理解這段程式的作用：

public User getUser(String userId) {
  var user = getFromCache(userId);
  if (user != null) {
    return user;
  } 

  user = userRepo.getUser(userId);

  setCache(userId, user);
  return user;
}

應該不難理解這就是用 userId 先嘗試從 cache 拿取 user，若 cache miss 則改從 db 拿取的一段程式碼。可以看到 getFromCache / setCache 是在相同的抽象層級，如此會讓程式碼容易閱讀，那怎麼樣是不同的抽象層級呢？

public User getUser(String userId) {
  var userCacheKey = "userEntity:" + userId;
  var user = null;  
  try {
    user = cache.get(userCacheKey);
  } catch (CacheMissException cme) {
    log.debug("cache miss, userId = {}", userId);
  }

  if (user != null) {
    return user;
  }

  user = userRepo.getUser(userId);
  setCache(userId, user);
  return user;
}

這段程式碼把原先的包在 getFromCache 的實作細節放在 getUser 這個層次，和 L15 的 setCache 是不同的抽象層級，這樣的程式碼反而比把下面全部實作都曝露在外的程式碼還要難以閱讀；因為想要 high-level 地了解這段程式在做什麼也不行，想要直接看到全部的細節也不行。

public User getUser(String userId) {
  var userCacheKey = "userEntity:" + userId;
  var user = null;  
  try {
    user = cache.get(userCacheKey);
  } catch (CacheMissException cme) {
    log.debug("cache miss, userId = {}", userId);
  }

  if (user != null) {
    return user;
  }

  user = userRepo.getUser(userId);

  try {
    cache.set(userCacheKey, user);
  } catch (Exception e) {
    log.debug("cache failed, userId = {}", userId);
  }
  return user;
}

實務上這種抽象程度不一致的情況履見不鮮，幾種可能：一是當時撰寫的工程式抽象功力不足，導致上下的抽象程度不對稱。但更可能的是，有一位工程師在修改下段 setCache 的例外處理時，覺得應該要以 method 將這段包起來，於是把整個 try-catch block 抽出去成 setCache，卻沒發現上面也應該要一起抽出去。在這麼小的一段程式碼大家可能會覺得「怎麼可能只抽下段不抽上段的 cache code」，但若是複雜一點的情況，或是原本的介面有點難處理時，有些工程師可能就只會「改一半」，老實說，我會認為要嘛整個改好，要嘛寧可不要改。

不寫註解、寫註解#

到底好的程式，需不需要寫註解？這是一個萬年大哉問。 google 搜尋這個問題，可以發現正反面的意見都有，我想這是任一工程師在工作上，一定會遇到的問題。

有些人看了 Uncle Bob 的 《Clean Code》 後，標榜著「Clean Code 就是不要寫註解」，我認為這是重大的誤會。其實《Clean Code》裡舉的例子，是那種會誤導別人、或根本是廢話的註解，比如解釋「這邊在做什麼」，都應該能透過程式手段 — 不論是好的命名、抽出 method、或是其他的方式 — 來處理，避免改了實作卻沒改到註解的情況。

但有一種註解我認為是要寫的：就是在一些不「自然」邏輯的處理上，去解釋「為什麼這邊要這樣做」。這種註解是要解釋做這件事情的意圖、意義，而通常會這樣做，是因為沒有什麼邏輯的商業需求或規定，又或者是某一段時間對某種情況的 workaround。當然，這必然要在版本控制中交代清楚，但能在程式碼中附上相關的票及脈絡，其實是增加可讀性的。

團隊能力的一致性#

這點，在外面的可讀性文章很少被提出來討論。為什麼前面會說，大神級的 code 也未必人人都懂呢？因為程式碼是由團隊維護，程式好不好讀是由團隊的程式水準決定的。有的時候前人寫了一個分層明確、合理、低耦合好擴展的架構，隨著人員流動，最後落入了程式能力較差的團隊中，對於這個團隊反而變成「不好讀」！

怎麼會如此？舉個比較極端的例子，一個才剛學會 if-else 的新手，因為對於程式的抽象功能還不了解，不可能會看得懂依照 Clean Architecture 寫出來的程式，反而義大利麵程式碼比較適合他。以剛才 getUser 的例子，若換成以下兩種寫法，你對於他們可讀性的評分是怎麼樣呢？

@Cached
public User getUser(String userId) {
  return userRepo.getUser(userId);
}



// UserController.java
interface UserController {
  User getUser(String userId);
}

// UserControllerImpl.java
public User getUser(String userId) {
  return userRepo.getUser(userId);
}

// CachedUserController.java
public User getUser(String userId) {
  var user = getFromCache(userId);
  if (user != null) {
    return user;
  }

  user = userController.getUser(userId);

  setCache(userId, user);
  return user;
}

這兩種方式都是能讓程式達到 Open-Closed Principle 的常見手法。第一段程式是用 Aspect-oriented programming (AOP) 的方式將 cache 存取邏輯包在實際向 db 存取 user 之外，但對於這不了解 AOP 的工程師來說，這簡直不可思議，甚至會覺得把這種東西藏在裡面到底在搞什麼鬼。可是對於有 AOP 經驗的工程師來說，這是很自然也合理的做法，也讓真正的業務邏輯不會被淹沒在 cache 存取這種重複性很高的實作細節之中，進而提升「可讀性」及程式的可擴展性。而第二段則是利用 proxy pattern 的方式做同樣的事情，但對於不清楚 proxy pattern 目的的工程師來說，在追蹤某個使用 UserController interface 的情境而想要看到真正的實作時，會覺得為什麼程式要寫得這麼繞、很難追蹤。

低耦合好擴展的程式，一定有許多的分層以及使用介面來做依賴反轉。在不明白程式碼架構、IDE 功能不熟悉、沒看到實作細節就無法理解、或是不習慣如此寫程式的工程師眼中，這樣的程式不好除錯（因為沒辦法很容易地跳到真正的實作）、看似同樣的東西「重複」做（但其實是為了分層），接著很可能就被這團隊魔改之後變成四不像，整個 code base 就又更難讀了。

因此，維持團隊能力和程式碼的一致，是非常重要的部分。甚至，一個好的工程師應該要遷就團隊能力，放棄更好的程式碼來換取整體團隊的維護能力，而不是孤芳自賞地寫只有自己看得懂，但其他人都看不懂的東西出來。但這並不表示好的工程師就應該要放棄寫好的程式，相反地，應該要為了能寫好的程式並讓團隊能夠維護，而去提升團隊整體程式功力！常見的方式有 Pair Programming、詳細的 Code Review、舉辦讀書會或是工作坊、凝聚大家撰寫程式時的模版共識…等等做法。如此，不僅能讓團隊能力提升、也增加自己在公司中的影響力，最重要的，是讓自己未來的日子變輕鬆！

所以，可讀性是？#

沒有所謂的「最好讀的程式」，可讀性是一個狀態、光譜，取決於「由什麼樣的人去讀」。我們要撰寫的，是讓維護團隊都能看得懂的程式。因此在撰寫程式時，換位成同事或是未來的自己、忘掉目前知道的所有事情，盡量保持一個 method 中的抽象程度一致，並為一些無法解釋的神奇商業邏輯加上註解。另一方面，協助團隊能力提升，讓大家理解並懂得欣賞好的程式架構及語言寫作方式，而非去寫團隊都沒辦法理解的高深程式碼，如此一來你的程式碼就不會難讀了。
